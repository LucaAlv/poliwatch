## Problem Statement

There is no single tool that gives a citizen a clear, current overview of what
German federal politics is actually doing — built from **primary sources**
(official Bundestag debate transcripts / Plenarprotokolle, draft and passed laws /
Drucksachen / Gesetzentwürfe, and roll-call votes / namentliche Abstimmungen)
rather than from news reports. The builder wants to know, at a glance: what is the
focus of current debates, which politicians took which stands, and how they voted —
because this information directly influences his own voting decisions. The itch is
personal, but the goal is a tool for a wider public audience. Not revenue-driven,
but open to later income from advanced features (richer visualizations, cross-checks
between parliamentary votes and politicians' social-media posts).

## What Makes This Cool

The "whoa" is the **coherent connected picture**: fragmented official activity —
a speech, a draft bill, a committee step, a roll-call vote — snapping into one
legible view of "what is happening in there right now, and who stood where."
Codex framed the north star well: **"Bloomberg Terminal for parliamentary
attention, with receipts"** — a daily civic radar, not a database. Every claim
the tool makes is one click from the exact Protokoll paragraph or Drucksache it
came from. The novelty is not access (the data is all public) — it is legibility
and connection, which is exactly the part that was prohibitively expensive before
LLMs and is why the prior attempt (offenesparlament.de) stalled as an accurate-but-
unreadable data dump.

## Constraints

- **Solo / small builder, side-project cadence.** Maintenance burden is the real
  enemy. The predecessor died of upkeep, not missing features. Keep the moving-parts
  count low.
- **Trust is existential.** This tool informs voting decisions. Perceived
  neutrality is survival. AI output must be non-authoritative and traceable.
- **Primary sources only.** No news reports as a data source.
- **Must stay current automatically.** A stale civic tool is worse than none.
- **Not built around profitability**, but architected so premium features can bolt
  on later without a rewrite.

## Premises

1. **Data is not the hard part.** Drafts, laws, transcripts, votes, and MP profiles
   are all reachable via the DIP API + abgeordnetenwatch + Bundestag Open Data +
   Open Discourse. The real work is the connective + analytical layer. (Agreed)
2. **The novel value is synthesis + connection, not any single view.** Single views
   are partly served already (abgeordnetenwatch = politicians/votes; Open Discourse =
   speeches; dawum = polls). You compete on coherence and UX. (Agreed)
3. **LLMs are why this is buildable now by a small team — and the main risk.**
   Transcript→summary, debate-focus extraction, and stance detection are cheap now;
   accuracy, neutrality, and hallucination are the central technical risk. (Agreed)
4. **Trust requires every AI claim to link back one click to the primary source.**
   A design constraint and a feature. (Agreed)
5. **Ship ONE launch lens even though the vision is all four.** The data spine serves
   all four; choosing which ships first is sequencing, not scope-cutting. (Agreed)

Launch lens chosen: **A — "The Pulse"** (what is the Bundestag focused on right now),
the one the builder would personally open daily.

## Cross-Model Perspective

An independent cold read (Codex, gpt-5.5, had not seen the conversation):

- **Coolest version:** a daily "Bundestag weather map" / civic radar — what's heating
  up vs. last week, who's driving the agenda, where the conflict is, what changed,
  what receipts exist. "Bloomberg Terminal for parliamentary attention, not a civic
  database."
- **Emotional center:** the coherent connected picture — fragmented official activity
  snapping into one connected political picture (not search, not summaries, not profiles).
- **50% head start:** Open Discourse (speaker-attributed parsed plenary speeches). The
  remaining 50% = topic grouping, trend detection, linking speeches→bills→votes, cited
  neutral summaries, a legible UI, the freshness pipeline, and the citation/trust layer.
- **Weekend build + hardest risk:** one daily Pulse page; hardest risk is LLM
  trustworthiness in topic labels/summaries — de-risk by making LLM output
  non-authoritative (every summary cites 3-5 source chunks shown beneath it, a "why
  this topic?" view, no stance claims unless directly supported by cited text).
  Goal: "Here is what the Bundestag spent attention on today, with receipts."

Where this design diverges from the cold read:
- **Topic detection:** Codex proposed embeddings + clustering for v1. This design
  starts **agenda-first** instead — the Plenarprotokoll is already segmented by the
  parliament into Tagesordnungspunkte (agenda items), so v1 gets topic segmentation
  for free and removes the least-reliable ML step. Clustering is deferred to v2.
- **Stack:** Codex proposed 4 components (Python + pgvector + FastAPI + Next.js).
  This design favors fewer moving parts at v1 to minimize maintenance burden.

## Approaches Considered

### Approach A: Agenda-First Pulse (minimal viable) — CHOSEN
Skip ML topic discovery. Use the parliament's own agenda-item segmentation (TOPs)
from the Plenarprotokoll as the "topics." Per TOP: LLM-summarize the speeches into
plain language, list speakers + party + a one-line stance, link everything to source.
"Attention" = speeches/time per TOP; trend = compare TOPs across sitting weeks.
- Effort: S/M. Risk: Low.
- Pros: hardest/flakiest step (topic detection) solved by parliament for free; fastest
  to a daily-usable page; bounded text per agenda item makes faithful summaries easy.
- Cons: topics are agenda-shaped, not cross-cutting themes; coarse trend detection;
  less emergent-clustering "magic."
- Reuses: DIP API Plenarprotokoll TOP structure + attached Drucksachen; Open Discourse
  for speaker/party backfill.

### Approach B: Clustering Pulse (ideal "weather map" architecture)
Full pipeline: ingest → chunk → embed → cluster recent speeches into emergent themes →
per theme label + summarize + rank attention + detect trend. Themes cross agenda items.
- Effort: L. Risk: Med. Most moving parts and highest maintenance burden; clustering
  quality is itself a research problem. Deferred to v2.

### Approach C: Spine-First, Thin Pulse on Top (creative/lateral)
Build the entity graph (MPs ↔ parties ↔ Vorgänge ↔ speeches ↔ votes) first, render the
Pulse as a thin query over it. Truest to the "connected picture" whoa but delays the
visible win and risks the platform-before-wedge trap that killed the predecessor.

## Recommended Approach

**Approach A, deliberately built so it grows into C.** Ship the agenda-first Pulse
fast (low risk, usable within days), but **model the persisted data as the entity graph
from day one** (MPs, parties, Vorgänge/bills, speeches, votes as linked records) even
while only rendering The Pulse. That way:
- The first visible win comes quickly (agenda-first, no clustering to babysit).
- Nothing is thrown away: lenses B (Politician), C (Bill Journey), D (Honest Compass)
  later become new *views/queries* over the same graph, not migrations.
- Maintenance surface stays small enough that the tool is still alive next year.
- Embeddings/clustering (Approach B) is added only after the agenda-first version's
  limits are actually felt.

This honors the "connected picture" whoa via the data model without over-building, and
avoids the trap that stalled offenesparlament.de.

## Open Questions

1. **Does agenda-first segmentation actually decompose cleanly in the data?** The whole
   Approach A thesis rests on the Plenarprotokoll reliably yielding agenda item →
   speakers+party → linked Drucksache. This is the riskiest assumption and is the
   subject of The Assignment below. Verify before writing product code.
2. **Stack choice not yet finalized.** Leaning toward fewer moving parts: a single
   TypeScript/Next.js app with API routes + Postgres (or SQLite to start), ingestion as
   scheduled scripts in the same repo; OR a thin Python ingestion service writing to the
   same DB the frontend reads. Decide at /plan-eng-review.
3. **Which LLM for summarization?** Default to the latest, most capable Claude model
   (e.g. Claude Opus / Sonnet 4.x via the Anthropic API) for faithful, citation-anchored
   summaries; revisit cost vs. a smaller model once volume per sitting week is known.
4. **Stance labeling — how far to go in v1?** Recommendation: in v1, show *who spoke and
   their party* and a one-line summary anchored to cited text; avoid algorithmic "stance
   scores" until the citation/trust UX is solid. Stance is a v2 feature.
5. **Freshness cadence.** Bundestag sits in concentrated sitting weeks. Confirm the
   ingestion trigger (poll DIP daily? on new Plenarprotokoll publication?) and how
   quickly a new sitting must appear in the Pulse.
6. **Neutrality positioning.** Decide early how the project presents its method and
   funding so the neutrality claim is credible (open method, sources visible, no
   editorializing). Worth a short "How this works / Sources" page at launch.

## Success Criteria

- **v1 is done when:** you can open one web page titled e.g. "Bundestag Pulse —
  {sitting date}", see the agenda items of the most recent sitting ranked by attention,
  and for each item read a plain-language summary plus the speakers (with party), with
  every summary one click from the exact Protokoll source. It updates automatically when
  a new Plenarprotokoll is published.
- **The honest test:** the builder actually opens it to decide what to pay attention to,
  instead of reading news first.
- **Trust test:** a skeptical stranger can verify any sentence on the page against the
  official source in one click.

## Distribution Plan

- **Deliverable type:** a public web service (website).
- **Hosting:** a low-maintenance host appropriate to the chosen stack (e.g. Vercel/Netlify
  for a Next.js app, or a small VPS/managed Postgres). Keep infra minimal.
- **Freshness pipeline (first-class, not an afterthought):** a scheduled job (GitHub
  Actions cron, or host-native scheduler) that polls the DIP API for new Plenarprotokolle,
  ingests them into the graph DB, generates summaries, and publishes. This pipeline is the
  thing that keeps the tool alive; treat its reliability as a launch requirement.
- **Discovery:** a memorable domain + a short "How this works / Sources" page that makes
  the primary-source, no-news method explicit (this is the differentiator and the trust
  anchor). Public-audience growth is a later concern; legibility + neutrality come first.

## Dependencies

- **DIP API key:** public key valid through May 2027 is enough to start; request a
  personal 10-year key (parlamentsdokumentation@bundestag.de) before launch.
- **Data sources:** DIP API (Vorgänge, Drucksachen incl. full text, Plenarprotokolle incl.
  full text, Personen, Aktivitäten); abgeordnetenwatch.de API v2 (politicians, mandates,
  committees, polls/votes — for later lenses); Bundestag Open Data (Plenarprotokolle/
  Drucksachen XML/JSON, namentliche Abstimmungen XLSX/XML); Open Discourse corpus
  (speaker-attributed speeches, for backfill/baseline).
- **LLM API:** Anthropic (Claude) for summarization; budget unknown until per-sitting
  volume is measured.
- **No blocking external dependency on offenesparlament.de** — treat as prior art only.

## The Assignment

**Before writing a single line of product code, validate the riskiest assumption by hand,
in one evening.** Grab the DIP API public key, pull **one** recent Plenarprotokoll (via
the API or Bundestag Open Data XML), and confirm — in a notebook or with curl/jq — that it
decomposes cleanly into:
(a) the agenda items / Tagesordnungspunkte,
(b) the speakers under each item, with their party, and
(c) the Drucksachen (drafts/laws) linked to each item.

If that one transcript cleanly yields "agenda item → speakers+party → linked bill," the
entire Approach A thesis holds and you can build with confidence. If it doesn't decompose
cleanly, you have found the real problem before spending a weekend on a product around a
broken assumption. Either outcome is a win. Timebox: one evening.
