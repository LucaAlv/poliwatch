## Problem Statement

The user's words: "I am not happy with the current state of the Datenbank view. I
don't think a lot of users will use it and even if demand is there, the current
implementation doesn't work well. I want to discuss and brainstorm if just deleting
the browser view of the database and just offering the download is the best way to
go forward here that will improve the ux and ui."

What `database.html` ("Datenbank erkunden") is today, measured on the 2026-09-14
build (15 tables, 229,473 rows, 291 MB store):

- **40,569 px tall.** One card per table with 12 sample rows. The `speeches` card
  alone is 10,236 px: 15 columns squeezed into 1,236 px, so text cells wrap one word
  per line and the `id` column wraps one digit per line. PR #49 fixed horizontal
  overflow by wrapping; this is what wrapping produced.
- The top ~950 px (header with "SQLite herunterladen", summary band, table chips,
  foreign-key panel) is readable and useful.
- No SQL runs in the browser; everything is a build-time snapshot
  (`render_database_page`, `scripts/build_dip_pulse_site.py:1110-1508`, plus
  `read_database_snapshot` :991, `render_database_unavailable_page` :1513,
  `DATABASE_TABLE_DESCRIPTIONS` :101).
- The only actionable element is the download button, and that same file is already
  linked from `index.html`, `puls.html`, `overview.html` and `sources.html`.

Audience, decided in session: **developers and researchers** who want the data itself.
Not a trust device for regular readers (the dossiers' XML/PDF links do that job), not a
debugging tool for the builder (`sqlite3` beats it).

Hosting reality (user's words): "It is hosted locally for now. But I don't want to make
design decisions now that I can't ship in a few weeks. I would like for this to work,
since I believe it would be a strong transparency signal, but if it doesn't work for v1,
that is not a deal breaker for me. If we can get this to work in a way that we can
reasonably ship to a larger audience in the next few weeks then lets keep it, otherwise
lets take it down from the website."

## What Makes This Cool

The page stops *showing* data and starts *proving* it. Five SQL recipes are executed
against the store during the build and rendered next to their top rows: who spoke most,
speaking share per Fraktion, who votes against their own Fraktion most often, the closest
roll-call votes, the procedures with the most speeches. Names link to MP pages, sittings to
dossiers, dossiers to the XML/PDF. A researcher copies the SQL, runs it against the file
they just downloaded, and gets the same rows. The recipes double as schema-drift tests:
if one errors against the store, the build fails; an empty result is a visible warning. Nobody in the open-parliament landscape does
this; sample rows finally have a reason to exist, and they are the *right* rows.

Underneath: the download shrinks from 291 MB to 166 MB raw / 47 MB gzipped, and is
publishable as a GitHub Release asset today, regardless of where the HTML ends up.

## Constraints

- Solo builder, side-project cadence; maintenance burden is the enemy (original design doc).
- Python stdlib only, no runtime dependencies; offline rebuild stays fast (today < 1 s).
  The export step runs only when the store, the recipes or the export format changed, or on
  `--export-data`; budget on the current 291 MB store: distribution copy ~5 s (measured),
  gzip of the 166 MB copy at `compresslevel=6` ~6 s (extrapolated from 10 s for 291 MB),
  15 CSV.gz files over 229k rows ~15 s (estimate; measure in step 6). Ceiling: 30 s.
- Trust is existential: every visible number on the page must come from the file offered
  for download, with build time and checksum shown.
- Must be shippable to a public audience within weeks without deciding the HTML host now.
- Must not grow the deployable site footprint (the generated site is already 2.4 GB; see
  "Out of scope").
- Schema and persist step untouched in this branch (premise 5, revised: an export-time
  *distribution copy* may blank one column).

## Premises

1. **The sample-row explorer has no audience.** Download + schema are what a
   developer/researcher needs; the dossiers already carry the receipts for readers. (Agreed)
2. **"Offering the download" is shippable within weeks, independent of the HTML host.**
   GitHub Releases: "Each file included in a release must be under 2 GiB. There is no limit
   on the total size of a release, nor bandwidth usage." GitHub Pages: "Published GitHub
   Pages sites may be no larger than 1 GB." The 47 MB gzip fits everywhere; the page links
   via a configurable data base URL that defaults to relative `data/exports/` for local
   preview. (Agreed)
3. **Doing nothing is a real cost.** The nav's "Datenbank" item leads to a page that reads
   as broken, and it is the page a technical visitor judges the project by. (Agreed)
4. **The site-wide 2.4 GB hosting problem is separate scope.** `data/bills.json` 386 MB,
   285 protocol JSONs 602 MB, `protocols/` 584 MB. This branch adds nothing to the
   deployable footprint; fixing site hosting is its own plan. (Agreed)
5. **Schema and persist untouched; the export step may ship a distribution copy with
   `speeches.paragraphs_json` blanked.** Revised after the cross-model challenge. Measured:
   `text` = 113.5 MB and `paragraphs_json` = 114.8 MB of the same words; nothing reads the
   column back (`build_dip_pulse_site.py:3791-3800` reads `snippet`, `char_count`, `page`,
   never `text` or `paragraphs_json`; the only writer is `persist_dip_pulse_store.py:744`).
   Dropping the column from the schema is a P2 TODO with its own migration, written into
   TODOS.md as part of this work. (Agreed, with the user's addition: "lets also address the
   issue with the paragraphs_json or at least lets note it in the todos")

## Cross-Model Perspective

Codex was quota-limited ("You've hit your usage limit"); the cold read ran as a Claude
subagent with fresh context (same harness, weaker independence). Its findings, close
paraphrase:

- **Coolest version not considered:** execute the recipes at build time and render the
  rows beside the SQL; result cells link into the site, which links to the primary source.
  Closes the receipts loop. Recipes double as schema-drift tests. (Adopted as the core of
  the recommended approach.)
- **What excites the user:** "I believe it would be a strong transparency signal." The
  download is proof the site has receipts; therefore a checksum, a Datenstand panel (build
  time, protocol range, row counts) and a versioned release matter more than 15 CSVs.
  (Adopted: Datenstand + sha256 are first-class; CSVs stay per the user's choice but are
  release assets, not part of the HTML deploy.)
- **50% project:** Datasette Lite over a CORS-served distribution file; the 50% to build
  is the stripped store, the page, and a verified CORS asset URL. (Deferred: depends on an
  unverified CORS assumption on release-asset redirects; the user ruled out in-browser SQL
  in session.)
- **Weekend build order:** export step → page rewrite → `--data-base-url` + release
  upload. (Adopted as Next Steps.)
- **Wrong premise:** #5's TODO half. Stripping `paragraphs_json` in the *export* touches
  neither schema nor persist. Predicted ~40 MB gzipped. **Verified in session:** the copy step took 5 s and produced
  165.8 MB raw; gzip -6 (the stdlib baseline this plan ships) gives 47.2 MB; zstd -19 would
  give 31.0 MB but is not stdlib and is not used. Prediction optimistic, direction correct;
  premise revised.

Where I disagree: Datasette Lite links are a stretch task, not a v1 dependency, and 166 MB
is borderline for a browser-loaded database anyway.

## Approaches Considered

### Approach A: Take it down, keep the file link
Remove the nav item, `database.html`, the three renderer functions (~520 lines), the
`index.html` area card and the overview/catalog/sources links; keep the existing "SQLite
herunterladen" links; preserve the work via git tag. Effort S (human ~2 h / CC ~10 min),
risk low. Rejected: leaves a 291 MB blob with no schema, Datenstand or checksum, which is
the opposite of the transparency signal the user wants, and does nothing about hostability.

### Approach B: Compact "Daten" page + distribution export + host-agnostic data URL (chosen)
See Recommended Approach. Effort M (human ~2 days / CC ~1 h), risk low-medium.

### Approach C: The dataset as a versioned product
B plus: page rendered from the manifest so page and release never disagree, `data-vYYYY.MM.DD`
release tags with DATA.md and LICENSE, a scheduled GitHub Actions workflow that builds and
publishes, Datasette Lite deep links once CORS is verified. Effort L (human ~1 week /
CC ~3 h), risk medium. Deferred: pulls CI secrets, the deploy target and an unverified CORS
assumption into a UI branch; most of its value arrives only once the site is public.

Ruled out in session: an in-browser sql.js query box (breaks the dependency-free rule and
needs a second trimmed store to maintain).

## Recommended Approach

**B.** One page, one export step, one deploy knob, one release script.

### The page (`database.html`, nav label "Daten")

Anatomy top to bottom (wireframe approved as-is, D10):

1. **Header + download panel.** Eyebrow "Rohdaten", h1 "Daten", two-sentence lede naming
   what is inside and that it is the same data the dossiers are rendered from; source and
   licence line. Right: primary button "SQLite herunterladen (47,2 MB)", file name, packed
   and unpacked size, the sha256 in a selectable `<code>` block (no copy button, no new
   script; the page keeps only the site-wide `page_scripts`), a collapsed `<details>` listing the 15
   `*.csv.gz` files with sizes, and one line stating that the distribution copy differs from
   the build store only by the blanked `speeches.paragraphs_json` column.
2. **Datenstand band.** Four tiles: build timestamp; protocol count with document-number
   and date range (today: 285, 20/100 to 21/84, 2022-01-27 to 2026-06-12); rows and tables
   and relationships (229,473 / 15 / 19); roll-call votes and individual votes (217 /
   154,015). Replaces today's summary band.
3. **Rezepte.** Five recipes, each a two-column block: title + SQL on the left, the
   executed rows on the right (`limit = 5`, fixed), with an optional one-line data caveat.
   Link keys are selected but not rendered as cells: R1 and R3 carry `mp_id`, R4 carries
   `document_number`, R5 carries `proceeding_id`, R2 has none. The renderer
   resolves them at render time and links a cell **only when the target page exists**:
   - `mp_id` → `abgeordnete/<canonical id>.html` through the lookup that
     `collect_abgeordnete` returns. Today that lookup (`build_dip_pulse_site.py:3953-3958`)
     is keyed by external ids (`aw:` / `dip:` / `xml:`, see `_mp_keys` :3696) and never by
     `mps.id`; this plan adds `lookup[f"id:{row['id']}"] = cid` in the same loop, for the
     same members that get a page. Raw `speeches.mp_id` is never turned into a URL
     directly, because `collect_abgeordnete` merges duplicate `mps` rows and writes only
     the canonical id's page.
   - `document_number` → `protocols/plenarprotokoll-<slug>.html` when that dossier is in
     `entries` (the same set `render_overview` links).
   - `proceeding_id` → `bills/bill-<proceeding_id>.html` when that slug is in the set of
     bill pages written by `write_bill_pages` (`bill_slug` :2865 builds `bill-<vorgang_id>`
     and `proceedings.id` is the DIP Vorgang id; `write_bill_pages` returns the slug set
     alongside `count`).
   Fixed caveats: R1 and R3 state that counts are per store row, not per consolidated
   person (a merged MP's profile page pools rows); R1 states that government members carry
   the DIP "Fraktion" `Regierung`. A recipe with zero rows (empty source tables in a narrow
   or un-enriched build, or nullable data such as `vote_fractions.leading_vote`) renders
   "keine Daten in diesem Build" and the build prints a warning; it never fails the build.
   The five recipes (exact SQL in the appendix), all verified against the current schema
   in session:
   - R1 Wer hielt die meisten Reden? (`speeches` × `mps` × `parties`, ORDER BY count)
   - R2 Redeanteil je Fraktion nach Zeichen (`SUM(char_count)` share)
   - R3 Abweichler: `vote_members.vote <> vote_fractions.leading_vote`, yes/no only
   - R4 Die knappsten namentlichen Abstimmungen (`ABS(yes_count - no_count)`)
   - R5 Vorgänge mit den meisten Reden (`proceedings` → `proceeding_positions` →
     `agenda_items` → `speeches`)
4. **So geht's los.** Two snippets: `gunzip` + `sqlite3 -header -column`, and
   `sqlite3` + `pandas.read_sql`.
5. **Schema + Beziehungen.** Left: the existing table chips (name + row count, anchors),
   then one compact card per table: description from `DATABASE_TABLE_DESCRIPTIONS`, a
   Spalte/Typ/Hinweis table where Hinweis shows PK, FK target (`→ mps.id`), NOT NULL,
   default; `CREATE TABLE` in a `<details>`; all cards collapsed except the first.
   Right: the existing foreign-key table, first 8 rows visible, the rest inside a
   `<details>` ("alle 19 Beziehungen"). **No sample rows anywhere; the filter box, its
   inline script and the `.sample-table` CSS are deleted.**
6. Footer as today ("statisch erzeugt, keine SQL-Abfragen im Browser").

`--no-persist` builds keep `render_database_unavailable_page` with updated copy ("Daten
nicht erzeugt").

### The export step

`export_distribution_data(database_path, exports_dir, *, recipes) -> DataManifest` in
`build_dip_pulse_site.py`, next to the page code, not in the persist script:

0. Contract: `export_distribution_data(database_path, exports_dir, *, recipes,
   force=False) -> DataManifest`. Called from `render_site` before any page is rendered,
   i.e. after every store write (`rebuild_database_from_entries` and the mp-pages
   `after_persist` roster ingest both run earlier in `main`). Returns the freshly written
   manifest, or the previous `datenstand.json` unchanged when the skip rule in step 5
   applies and `force` is false. Raises on a recipe SQL error (schema drift). Not called at
   all for `--no-persist`. No SQLite version gate: the copy uses
   `sqlite3.Connection.backup()` (Python 3.7+, any SQLite version), so there is no
   old-SQLite fallback to render.
1. From a read-only connection (`file:…?mode=ro`), `backup()` into
   `exports_dir/.dist.tmp` (one pass over the source); on the temp copy, `UPDATE speeches
   SET paragraphs_json = '[]'` then `VACUUM` in place; `gzip.open(...,
   compresslevel=6)` to `bundestag-pulse.sqlite.gz.tmp`; `replace()` into place; delete
   the uncompressed temp copy. Same `.tmp` + `replace()` discipline as
   `rebuild_database_from_entries`.
2. For every table (same `sqlite_schema` walk as `read_database_snapshot`): stream rows
   through `csv.writer` into `<table>.csv.gz` (UTF-8, header row, `NULL` as empty string,
   `paragraphs_json` written as `[]` for consistency with the distribution store).
3. Execute each recipe's SQL **verbatim** against the *distribution* copy (not the build
   store); the `LIMIT 5` is part of the shipped SQL text and is what the page displays, so
   nothing is appended at run time. A recipe that raises an `sqlite3` error fails the build with the recipe id
   and the SQLite message: that is the schema-drift check. A recipe that returns zero rows
   never fails the build: the manifest records `"rows": []` and
   `"empty_reason": "keine Daten in diesem Build"`, and the build prints a warning naming
   the recipe (zero rows can come from empty tables in a narrow build or from nullable
   data, e.g. `vote_fractions.leading_vote`, which `persist_dip_pulse_store.py:841` writes
   through `clean()`).
4. Write `exports_dir/datenstand.json` (shape below), then unlink every file in
   `exports_dir` that the new manifest does not name (a renamed or dropped table, a format
   bump), the way `write_bill_pages` removes stale bill pages. `protocols.first/last` are
   the first and last protocols by `protocol_sort_key`; `from/to` are their dates.
   What renders from where: download sizes, sha256, Datenstand and Rezepte come from this
   manifest, so page and files cannot disagree; the schema cards, chips and the
   foreign-key table come from `read_database_snapshot` on the build store (the manifest
   does not carry column types or `CREATE TABLE`), with `sample_limit=0` so no rows are
   read.
5. Skipped entirely when `--no-persist`. Otherwise the export runs when any of these differ
   from the previous manifest: `source_mtime_ns`, `source_bytes`, `recipes_hash` (sha256
   over the recipe ids + SQL), `export_format` (an integer bumped whenever the CSV layout or
   the distribution transform changes); or when `--export-data` forces it. An unchanged
   store with unchanged recipes keeps offline UI rebuilds sub-second.

```json
{

  "generated_at": "2026-09-16T00:21:22+00:00",
  "source_mtime_ns": 1785851520000000000,
```

Default `exports_dir` = `OUTPUT_DIR/data/exports/`. It is served by the local preview
server so downloads work on `localhost`.

### The deploy knob and the release path

- `--data-base-url URL` (env `DIP_PULSE_DATA_BASE_URL`), default `data/exports/`. Every
  download link on the page, and the existing `database_href` "SQLite herunterladen"
  links on `index.html`, `puls.html`, `overview.html`, `sources.html`, are built from it
  and point at the `.gz` distribution file named in the manifest. When there is no
  manifest (`--no-persist`), `database_href` is `None` and those pages omit the link, as
  they do today. A value is absolute when it matches
  `^[a-z][a-z0-9+.-]*://` or starts with `/`; it is used verbatim (with a trailing `/`
  added if missing). Anything else is a path relative to the site root; every consumer of
  it is a depth-0 page (`render_site`, :5747-5785), so no depth prefixing is needed and
  none is built.
- **Drift guard (superseded in review by `--data-manifest`, DX6.1).** The page's sizes and
  sha256 describe the files in `data/exports/`, not whatever a release holds. The deploy
  sequence is therefore: (1) a full build that produces the exports, (2)
  `publish_dip_pulse_data.sh` uploads them and saves the uploaded manifest back as
  `data/exports/published.json`, (3) an `--offline` rebuild with
  `--data-manifest data/exports/published.json --data-base-url <release URL>`, so the page
  renders from the manifest the release actually holds and cannot drift from it. The
  originally planned "loud warning when a build with an absolute base URL re-exports" was
  replaced by this explicit manifest selection; `--data-base-url` only decides where links
  point.
- **Separable second PR (release tooling, not UI):** `scripts/publish_dip_pulse_data.sh`:
  `gh release create --notes-file` (or reuse an existing tag) then `gh release upload
  --clobber` for the `.gz`, the CSVs and `datenstand.json`; prints the
  `releases/download/<tag>/` base URL to pass as `--data-base-url` on the deploy build.
  Requires `gh` auth; no CI. README §7 (hosting) gains: exclude `data/exports/` from the
  HTML deploy when the host caps file size, pass `--data-base-url`, run the publish
  script. Documented as the v1 shipping path; the 2.4 GB site question is referenced, not
  solved. The page and the flag ship in PR 1 and work without PR 2.

## Open Questions

- **Licence line.** The page needs one sentence on reuse terms for DIP data, bundestag.de
  roll-call data and abgeordnetenwatch profile links. Today `sources.html` describes sources
  but not a licence. Decide the wording before the page ships; until then the line reads
  "Lizenzhinweis: siehe Quellen und Methode".
- **CORS on release assets.** Only matters for the deferred Datasette Lite links; check
  with `curl -I` on the first published asset (see The Assignment).
- **zstd vs gzip.** zstd -19 gives 31 MB vs 47 MB, but gzip is stdlib and universally
  installed; ship gzip in v1, revisit if bandwidth matters.
- **Name format in recipe rows.** R3 shows roster-style "Seidler, Stefan" while R1 shows
  "Olaf Scholz"; that is the identity-consolidation gap already known on the MP pages,
  surfaced honestly. Decide whether the page notes it (the per-row caveat already says
  counts are per store row).

## Success Criteria

- ~~`database.html` renders under 4,000 px tall at 1280 px wide~~ **not met, measured
  2026-09-18 on the real 285-protocol / 17-table build: 7,405 px at 1280 px** (down from
  40,569 px — an 82% reduction — but over the original 4,000 px target). The 4,000 px
  number came from a wireframe with "abbreviated schema cards"; the approved design
  addendum's D1.1 (hard rejection #7) requires every table's name, row count and
  description always visible with two sibling `<details>` per table, which alone measures
  190.6 px × 17 tables = 3,240 px, before the header/Datenstand/five recipes/So-geht's-los
  sections (~4,165 px). No cell wraps one word per line at 1280/1024/900/375 px (verified
  with Playwright screenshots against the real store); the page never grows a horizontal
  scrollbar at 375 px. Heights at the other three widths: 1024 px → 8,504 px; 900 px →
  8,882 px; 375 px → 11,890 px (taller because the header and Datenstand stack to one
  column). Fixing the 4,000 px target without weakening D1.1 would mean collapsing schema
  rows behind a single top-level `<details>` per table — the exact anti-pattern D1.1 was
  written to reject — so this is recorded as a known miss rather than silently patched.
- Five recipes execute at build time and their rows match a manual `sqlite3` run against
  the downloaded file — verified: R4 run directly against the published
  `bundestag-pulse-local.sqlite.gz` returns the identical five rows the page shows
  (2025-01-29 Entschließungsantrag der Fraktion der CDU/CSU, 348:344, …).
- Distribution file ≤ 50 MB gzipped on the current store — **47.2 MB**, exactly matching
  the design doc's earlier 5-second experiment; sha256 on the page matches the file (the
  page's `<code class="sha">` is byte-for-byte the file's sha256, asserted by
  `test_daten_export.py::test_manifest_file_sha256_matches_the_file_on_disk` and confirmed
  by hand on the real 47.2 MB file).
- A public deploy is possible with two commands: `publish_dip_pulse_data.sh`, then a build
  with `--data-base-url` pointing at the release. **Deferred to PR 2** (out of scope for
  this implementation pass); local preview works with no flags, confirmed on the real store.
- Offline UI rebuild stays under 1 s when store, recipes and export format are unchanged —
  **not met as measured, but not caused by the export step**: the export step itself skip-
  reuses correctly (`export: reused data/exports (unchanged)`, sub-second), but the *whole*

## Appendix: the five recipes as executed (verified 2026-09-15 on the 285-protocol store)

Each recipe declares its link-key columns, which are selected but not rendered.

```sql
-- r1-meiste-reden · link_key: mp_id
SELECT m.id AS mp_id, m.display_name, p.name AS fraktion,
       COUNT(*) AS reden, SUM(s.char_count) AS zeichen
FROM speeches s
JOIN mps m ON m.id = s.mp_id
LEFT JOIN parties p ON p.id = m.party_id
GROUP BY m.id
ORDER BY reden DESC, zeichen DESC, m.id
LIMIT 5;

-- r2-redeanteil-fraktion · link_key: none
SELECT p.name AS fraktion, COUNT(*) AS reden,
       ROUND(100.0 * SUM(s.char_count) / (SELECT SUM(char_count) FROM speeches), 1) AS anteil_prozent
FROM speeches s
JOIN mps m ON m.id = s.mp_id
JOIN parties p ON p.id = m.party_id
GROUP BY p.id
ORDER BY reden DESC, p.name
LIMIT 5;

-- r3-abweichler · link_key: mp_id
-- vote values in the store: yes / no / abstain / absent; leading_vote may be any of them.
SELECT m.id AS mp_id, m.display_name, p.name AS fraktion, COUNT(*) AS abweichungen
FROM vote_members vm
JOIN vote_fractions vf ON vf.vote_id = vm.vote_id AND vf.party_id = vm.party_id
JOIN mps m ON m.id = vm.mp_id
JOIN parties p ON p.id = vm.party_id
WHERE vm.vote IN ('yes', 'no')
  AND vf.leading_vote IN ('yes', 'no')
  AND vm.vote <> vf.leading_vote
GROUP BY m.id
ORDER BY abweichungen DESC, m.display_name
LIMIT 5;

-- r4-knappste-abstimmungen · link_key: document_number (no vote page exists)
-- A vote can hang on several agenda items; MIN() picks one dossier deterministically.
SELECT MIN(p.document_number) AS document_number,
       v.date, v.title, v.yes_count AS ja, v.no_count AS nein,
       ABS(v.yes_count - v.no_count) AS differenz
FROM votes v
LEFT JOIN agenda_item_votes aiv ON aiv.vote_id = v.id
LEFT JOIN agenda_items ai ON ai.id = aiv.agenda_item_id
LEFT JOIN protocols p ON p.id = ai.protocol_id
GROUP BY v.id
ORDER BY differenz ASC, v.date DESC, v.id
LIMIT 5;

-- r5-vorgaenge-meiste-reden · link_key: proceeding_id
SELECT pr.id AS proceeding_id, pr.title, pr.proceeding_type AS typ,
       COUNT(DISTINCT s.id) AS reden, COUNT(DISTINCT ai.protocol_id) AS sitzungen
FROM proceedings pr
JOIN proceeding_positions pp ON pp.proceeding_id = pr.id
JOIN agenda_items ai ON ai.id = pp.agenda_item_id
JOIN speeches s ON s.agenda_item_id = ai.id
GROUP BY pr.id
ORDER BY reden DESC, sitzungen DESC, pr.id
LIMIT 5;
```
