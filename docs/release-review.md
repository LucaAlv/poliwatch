# Release review checklist

A main release becomes stable when the owner has run every step below on it and the record `docs/release-reviews/<version>.md` says "stable". Run it about every three months (plan decision Q3, `docs/plans/release-readiness.md`). The first release is reviewed in full and is the first stable. What main and stable releases are, and what may change between releases, is in `docs/release-policy.md`; the record starts from `docs/release-reviews/TEMPLATE.md`.

**Inputs.**
- The candidate's release directory `data-<version>/`, checked with `shasum -a 256 -c SHA256SUMS`. Its SQLite is the asset `bundestag-pulse-<version>.sqlite.gz`.
- The last stable's release directory (none for the first).
- The source XML of the candidate's sittings: `data/xml/` of the site output directory the release was built from.
- CPP-BT's newest speech metadata from Zenodo (`CPP-BT_<date>_DE_CSV_Reden_Metadaten.zip`, concept DOI 10.5281/zenodo.4542661, CC0). Download it with the owner's approval, and record its version and SHA-256 in the review record. Never commit it.

**1. Coverage per year.** From the candidate's DATA.md, "Abdeckung nach Jahr und zurückgehaltene Reden" and "Ausgeschlossene Sitzungen":
- every exclusion's Grund reads „Fehler der Quelle, der die ganze Sitzung betrifft“ (`source_defect`) or „Ein Fehler, der sich nicht auf einzelne Reden eingrenzen lässt“ (`not_narrowable`); a „Wartet auf …“ Grund (`awaiting_rule`, `awaiting_acquisition`) stops the review. DATA.md prints these labels, not the keys (`EXCLUSION_REASONS` in `scripts/build_dip_pulse_site.py`);
- per year: sittings, Reden stored, Reden withheld, share withheld. Compared with the last stable, explain every year whose sittings fell or whose withheld share rose;
- per Wahlperiode: our sittings against CPP-BT's (step 4 prints both).

**2. Figures moved since the last stable.** `scripts/compare_store_values.py` takes two site output directories (each holding `data/bundestag-pulse.sqlite`). Use the candidate's output directory, and for the last stable a scratch directory with its SQLite unpacked to `<dir>/data/bundestag-pulse.sqlite`. Run it with `--cohort shared` and again with `--cohort all`. Pages read "unavailable", which is expected. Every value that moved in the shared cohort must be named by a correction in some release's `changes.json` between the two, or follow from a rule change the CHANGELOG names. An unexplained move is a bug (see "A bug found in review").

**3. Spot checks against the protocols.** Draw five sittings with a seed written into the record: one per Wahlperiode, plus the newest. The size of five was signed off by the owner on 2026-11-21. In each, check against the protocol PDF:
- five Reden: Redner, Fraktion, TOP, and the opening and closing sentence;
- every withheld Rede: its reason, and that the text is the printed one;
- up to three named votes: the tally against the bundestag.de page, and the linked TOPs.

Also check every sitting that changed its status since the last stable (newly held, newly withheld Reden, released Reden).

**4. Comparison with CPP-BT, per sitting.**

```bash
python3 scripts/compare_cpp_bt.py --export <candidate sqlite or .sqlite.gz> --xml-dir <site output>/data/xml \
  --cpp-bt <CPP-BT zip> --out docs/release-reviews/<version>-cpp-bt.tsv
```

The script uses only the standard library and imports nothing of this project. It writes three blocks into one TSV (blocks start with a `# ` line): one row per sitting (an empty cell means that side does not hold the sitting, which is not zero), one row per difference with a `status`, and a summary with the SHA-256 of the export and of the CPP-BT file and the number of XML files read. It exits 0 whenever it compared, and 2 when an input is unreadable or nothing could be compared (no sitting held by both sides, over 1% of CPP-BT rows with no readable protocol number or `rede_id`, or no token count that parses), so a changed CPP-BT format cannot read as a pass. It writes the report whole or not at all, and refuses an `--out` that is one of its inputs. The join rules are the script's own `sitting_key()` and `source_rede_id()`: a trailing ` (neu)` is dropped from CPP-BT's protocol number, `:N` from our `rede_id`, and `nested:` ids and ids without a value (Fragestunde) are skipped by name and counted in the summary. Pass when:
- no row has the kind `only_ours`, and the summary line `ids_only_ours` is 0: no `rede_id` of ours is missing from CPP-BT in a sitting both hold;
- every id only CPP-BT has carries a class. `withheld`, `paragraph_31`, `paragraph_31_continuation` and `reprint` pass as `classified`. `in_top_presidium`, `in_top_other`, `annex_zu_protokoll`, `annex_other`, `outside_top` and `unclassified` are read by hand unless `scripts/cpp_bt_known_differences.tsv` lists the id with a reason (`status` `known`; an `only_theirs` row must name its `rede_id`, and the script refuses the file otherwise). The 82 `in_top_other` ids of the first run are listed there: 81 reviewed procedural units (ADR 0004) and 21/43 `ID214301700`. T4's measure step (2026-11-18) added 77 more only-theirs ids: 40 reviewed procedural or chairing units and the 37 § 31 declarations of 18/158 (E9);
- surname and Fraktion differ on a shared id only where `scripts/cpp_bt_known_differences.tsv` lists the pair (spellings and name changes, each with a reason; `docs/source-errors.md` C5 for the one Fraktion row, 20/94 `ID209407600`). Any other is `read_by_hand`. The Fraktion row for 18/222 `ID1822204600` (C6) was removed after v0.46.9.0 stored the printed Fraktion without the spoken text; it is not kept as a guard, because a row that matched the old wrong label would mark a return of that label as known instead of showing it. A surname agrees when every word of CPP-BT's surname is a word of our name, a hyphen counting as a separator;
- what was not compared is written into the record and explained, not only what differed. The summary prints `surname_not_compared` (a shared id whose Rede has no `mp_id` on our side, so no name, or whose surname CPP-BT leaves `NA`), `fraktion_not_compared` (a shared id with no Fraktion label on one side; 10,098 of 81,446 on 2026-11-22) and the `redner_id_not_compared_*` counts below, next to the matching `_compared` counts. Put all of them in the record beside the last stable's. A count that rose is explained (which sittings, and why) before the candidate passes. No ceiling is set: a ceiling would be a new threshold, which needs the owner's sign-off;
- Redner-ID agreement, `redner_id_*` in the summary, reported and not a pass condition: over the ids both sides hold in a sitting both hold, in `speeches` and `contributions` (not `withheld_units`), on the row without `:N` (the element's own speaker), with a non-empty, non-`NA` id on both sides, `redner_id_agree` agree and `redner_id_differ` differ, `redner_id_differ_theirs_10000` of them with CPP-BT's `10000` (a value its codebook says is issued more than once). Our id is `mps.xml_redner_id` of the row's `mp_id`. The summary's `redner_id_definition` line says the same and the `redner_id_not_compared_*` counts say what was left out and why (`ours_empty`: no `mp_id`, or the person has no `xml_redner_id`; `ours_no_own_row`: only a `:N` part of the element is stored, whose speaker is not the element's; `theirs_empty`). Each differing id is a `redner_id` row with status `reported`; read them when the count moved since the last stable;
- word-to-token ratio: a shared Rede over 50 CPP-BT tokens whose ours-words to their-tokens ratio differs from its sitting's median by more than 15% is listed as `ratio` (a sitting whose median is 0 lists all its Reden; a Rede with no stored text counts 0 words and is listed; the unattributed speech 19/2 `ID19205800` is one, `docs/source-errors.md` E2). Within a sitting the `ratio` rows come largest deviation first; to find the 20 largest overall, sort all `ratio` rows by the deviation in their `detail` column, and read those 20. The ratio is a lead on text, not a verdict: of the first run's largest, three were read (19/72, 19/7, 18/44) and are Reden whose XML element holds what follows the speech, such as the whole debate, of the kind `docs/source-errors.md` C1 describes. **The two thresholds (15%, 50 tokens) were signed off by the owner on 2026-11-21**, on the first run (`docs/release-reviews/cpp-bt-first-run-2026-11-14.md`: 1,487 of 53,819 Reden listed; 1,862 of 60,111 after T4). Re-run at every stable review and look again if the listed count jumps.

CPP-BT is automatic too and does not check deeply. Agreement is no proof both are right; disagreement is a lead. The comparison covers units that carry a `rede_id`, so Fragestunde turns and the text itself are outside it.

**5. Claims.** DATA.md, "Vergleich mit anderen Datensätzen und Verknüpfung" (authored in `docs/data-methods.md`):
- Re-check the "Vergleich" table against each dataset's own page when its date is more than six months before the candidate, or when step 4 used a newer CPP-BT version than the table names. Update the cells, the sources list and the date. A cell nobody could verify reads „nicht angegeben“ or „nicht gelesen“, never a guess.
- The figures under "Verknüpfung über die Kennungen des Bundestages" are a dated measurement. Compare them with step 4's summary block for the candidate. If the candidate holds other sittings or CPP-BT has a newer version, replace the figures and their date in the next main release; the candidate's DATA.md stays as it is, since its date says which state it measured. The Redner-ID agreement is step 4's `redner_id_agree` of `redner_id_compared` and `redner_id_differ` (with `redner_id_differ_theirs_10000`); copy those, do not recount by hand.
- Check that the licence section still names the open roll-call question, or its answer.

**6. Verdict.** Write the record's part 6: the findings with their fix release (a table, empty if none) and the verdict, stable or not and why. The inputs and digests and each step's result are parts "Inputs" and 1 to 5 of the record. Then tag `stable-<version>` on the commit of `data-<version>`, and archive the release on Zenodo once that exists.

**A bug found in review.** The candidate is not patched and does not become stable. The fix goes into a new main release. Replay the fix on a copy of the store (README, "Validate a data correction") and check that only the figures it should move moved. That release's `changes.json` names the correction, and steps 2 and 4 run again on the new release, limited to what the fix touches. The new release then becomes stable. Until then the last stable stays the stable one.
